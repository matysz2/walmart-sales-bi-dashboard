# Walmart Sales Performance Analysis

End-to-end Business Intelligence project built with **Microsoft SQL Server, T-SQL, Power Query, Power BI, DAX, Power BI Service, Git and GitHub**.

The project covers the complete analytical workflow: source-data audit, cleaning, relational modeling, SQL analysis, reporting-layer preparation, Power BI semantic modeling, DAX measures, interactive reporting, Row-Level Security, deployment to Power BI Service, gateway configuration, refresh testing, performance analysis and mobile optimization.

---

## Project Overview

The goal of this project is to analyze Walmart historical sales data and build a reusable BI solution for monitoring store performance.

The solution enables analysis of:

- total and average sales,
- sales trends over time,
- year-over-year performance,
- holiday vs non-holiday sales,
- store rankings,
- store-type performance,
- selected-store context,
- detailed store performance,
- secure access with Row-Level Security.

The project was developed as a portfolio project for **Junior Data Analyst, BI Analyst and SQL Analyst** roles.

---

## Business Goal

The business objective is to provide management with a clear view of sales performance across stores and time periods.

The report is designed to support questions such as:

1. Which stores generate the highest total sales?
2. How does sales performance change over time?
3. How does current sales performance compare with the previous year?
4. Which store types generate the highest sales?
5. Are holiday weeks different from non-holiday weeks?
6. Which stores rank highest within the selected context?
7. What share of selected sales is generated by each store?
8. How does an individual store perform over time?
9. Which KPI values should be monitored by management?
10. How can report access be restricted for different users?

## SQL Reporting Layer

The reporting layer prepares reusable datasets for business reporting.

It includes:

- enriched sales data,
- sales summaries by store,
- ranking by total sales,
- best-performing weeks,
- week-over-week changes,
- holiday vs non-holiday comparisons,
- parameterized reports,
- indexes supporting common filters,
- optimized date-range filtering.

Example SARGable date filter:

```sql
WHERE Date_Sales >= '20110101'
  AND Date_Sales <  '20120101';
```

This pattern is preferred over:

```sql
WHERE YEAR(Date_Sales) = 2011;
```

because range filtering can use an index on `Date_Sales` more effectively.

## DAX Measures

The report contains measures for sales, time intelligence, ranking and context analysis.

### Total Sales

```DAX
Total Sales =
SUM(Walmart_Sales_Cleaned[Weekly_Sales])
```

### Stores Count

```DAX
Stores Count =
DISTINCTCOUNT(Walmart_Sales_Cleaned[Store])
```

### Sales Previous Year

```DAX
Sales Previous Year =
CALCULATE(
    [Total Sales],
    SAMEPERIODLASTYEAR(Dim_Date[Date])
)
```

### Sales YoY %

```DAX
Sales YoY % =
DIVIDE(
    [Total Sales] - [Sales Previous Year],
    [Sales Previous Year]
)
```

Other implemented areas include:

- YTD calculations,
- holiday sales measures,
- non-holiday sales measures,
- store rankings,
- selected-context rankings,
- store sales share,
- selected-store sales share,
- previous-year comparisons.

## Incremental Refresh Demonstration

Incremental Refresh was implemented as a technical demonstration.

The training dataset contains only 6,435 cleaned fact rows, so Incremental Refresh is not required for performance in the final portfolio model.

During the exercise:

- `RangeStart` and `RangeEnd` were created,
- a Date/Time filter was applied,
- Incremental Refresh policy was configured,
- the model was published to Power BI Service,
- refresh history was validated.

Observed refresh times in the exercise:

- first manual refresh: approximately **3 min 40 s**,
- next manual refresh: approximately **16 s**.

The temporary Incremental Refresh test table was removed from the final portfolio model to keep the semantic model clean.

## Key Findings

The analysis produced several business observations:

- Store 20 generated the highest total sales across the full dataset.
- Store size showed the strongest positive relationship with weekly sales in the exploratory analysis, with correlation of approximately `0.81`.
- Holiday weeks had higher average weekly sales than non-holiday weeks.
- Total non-holiday sales were higher because the dataset contains substantially more non-holiday observations.
- Store type and store size should be considered together when interpreting store performance.
- Correlation between store size and sales does not prove that increasing store size directly causes higher sales.

The Power BI report adds interactive analysis by year, store type and store selection.
